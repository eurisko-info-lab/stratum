# F5 — constitution-relative governance

```text
governance: add claims proofs and acceptance in F5
```

## Feature

Repository changes become constitutionally accepted rather than merely
well formed.

$$
F_5 = F_4 + \text{constitution-relative governance}
$$

## Meta change

[features/governance/governance.meta](../../features/governance/governance.meta)
declares `Signer`, `Claim`, `ProofGoal`, `ProofTerm`, `TestEvidence`,
`Authority`, `AuthorityScope`, `AcceptanceConstitution`, `AcceptanceDecision`,
`ResourceProfile` and `Proposal`, with the judgments `CheckAuthority`,
`CheckSignature`, `CheckTests`, `CheckProof` and `EvaluateAcceptance`.

## Cryptography boundary

The host answers `sign`, `verify` and `public-key` as generic capabilities and
verifies the cryptographic equation only. Meta decides entitlement, scope,
subject binding, expiry, acceptable evidence, required tests, the decision
procedure and resource limits.

## Subject binding

$$
\mathsf{subject}(p, K) = (\mathsf{patch}(p), \mathsf{predecessor}(p), \mathsf{name}(K))
$$

Acceptance evidence therefore binds the exact patch digest, the exact
predecessor, the exact constitution, the exact entitled party and the exact
proof or test evidence.

## Constitutions

| Constitution | Requirements |
| --- | --- |
| `local` | kind, authority, signature |
| `tested` | kind, authority, signature, tests |
| `proved` | kind, authority, signature, proof |
| `meta-governance` | kind, authority, signature, tests, proof, budget |

Meta and Grammar changes are governed by `meta-governance`, which is strictly
stronger than the ordinary code constitution.

## Proof checking

Proof terms are checked, not trusted. `axiom` steps must be justified by the
proposal's claims and `modusPonens` steps must match a derived implication and
its antecedent exactly.

## Repository integration

A branch may hold proposed but unaccepted patches. `PublishableBranch` blocks
promotion until every decision is accepted.
